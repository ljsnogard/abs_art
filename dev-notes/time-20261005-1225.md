# 计时能力（`TrTime`）：trait 在 `abs_art`，实现在三个后端

日期：2026-10-05 12:25
性质：**设计决策 + 实现记录**（本次已落地，分支 `feat/time`）。
来源：`smux_v1` 的保活（T6）需要一个「等一段时间」的能力，而它手上只有
`abs_art`；`smux_v1/src/time` 里那套轮盘式计时器是**没有这个能力时的补救**。
因此把**能力**补进 `abs_art` 家族，消费方再按新能力使用。

> **后记（2026-10-05 16:15）**：本文「把 `TrDelay` / `TrTime` 实现挂在三个后端的
> `LocalScope` 上」这一形状**已被重新讨论**——`Delay` 与本地/全局调度无关，挂在
> 「本地队列的值」上属于建模错位。两条收尾路线（环境化 / `TrLocalScope::Runtime`
> 投影）、以及配套的 `TrClock` 构想，见 `bridge-scope-clock-20261005-1615.md` §2/§3。
> 本文其余内容（为什么 `abs_art` 不暴露 `Instant`、`TrTime` 的契约）仍然有效。

---

## 0. 一句话

`abs_art` 只加 **trait**（零依赖、`no_std`、无 alloc），三个后端各自用自家计时器
实现它；**没有**把 `smux_v1` 那个轮盘搬进来。

## 1. 公开面（`abs_art::time`，本次新增）

| 项 | 形状 | 归属 |
| --- | --- | --- |
| `TrTime: TrDelay` | `fn interval(Duration) -> impl TrInterval` + `fn timeout(Duration, F)`（默认方法）。**一次性睡眠不另起名字**：就是 [`TrDelay::delay`]——两条曾短暂分歧，已收敛 | 抽象（trait） |
| `TrInterval` | `fn tick(&mut self) -> impl Future<Output = ()>` | 抽象（trait） |
| `Elapsed` | 超时失败；`Debug + Display("期限已到") + core::error::Error`，字段私有 | 抽象（零依赖手写） |
| `TrTime::timeout` | `(Duration, F) -> Result<F::Output, Elapsed>`，**trait 的默认方法**（挂在运行时类型上） | 抽象（一份实现） |

三个方法/函数都是**关联函数**（不收 `self`），与既有 `TrDelay` 同形：计时源来自
运行时的线程本地上下文，不需要由值携带，因此业务库只穿**类型**、不必先拿计时器值。

后端（`abs_art-tokio` / `abs_art-compio` / `abs_art-smol`）各新增 `time` 模块：

- `impl TrTime for Runtime<CAPS> where [(); CAPS]: HasDelay`（与 `TrDelay` 同一门控）；
- `impl TrTime for LocalScope`（**额外**一格，见 §5）。

## 2. 因果链：为什么抽象层**不暴露 `Instant`**

`abs_art` 是 `no_std` + **零依赖**（连 `[features]` 段都没有，也没有 `alloc`）。它
既不能写 `std::time::Instant`，也不该为此引入一个外部时钟抽象 crate——那会让那个
crate 变成 `abs_art` 的**公开依赖**（全家族都得对齐版本），正是本项目已经警惕过的
那类耦合。

于是把「绝对时刻」留给**持有自己时钟**的消费方，而它们本来就需要一个时钟
（连接级 epoch、每子流「最后活动」毫秒等记账都要它）。三个绝对形式都是**可推导**的：

```text
sleep_until(t)  ≡  sleep(t − clock.now())
timeout_at(t)   ≡  timeout(t − clock.now(), future)
interval_at(s)  ≡  sleep(s − clock.now()) 之后接 interval(period)
```

附带的好处比「省一个 trait」更大：**消费方可以注入假时钟**。`TrTime` 是
`Duration`-only 的，因此测试里写一个「`sleep(d)` 把虚拟时钟推进 `d` 后立刻就绪」的
假后端即可，超时/周期/宽限期的判定全部确定化，不依赖任何真实调度——`abs_art` 自己
的单测就是这么做的（`FakeTime_`）。

## 3. 语义契约（三后端必须一致）

「一份 trait、三个实现」最容易出的问题是**语义漂移**。以下六条是**契约**，由
`abs_art-smoke/tests/time_contract.rs`（3 后端 × 5 用例 = 15 格，全绿）钉住：

1. `sleep(d)` 不早于 `d` 返回；
2. `interval` 的**第一次** `tick` **立即**完成（起点 = 调用的那一刻）；
3. 其后**相位对齐**到起点（`起点 + k × period`），不是「上一次 tick 之后再等一个 period」；
4. 落后时**跳过**已错过的时刻（不连续补齐）；
5. `period == 0` 时 `interval` **panic**；
6. `timeout` 在同一轮里两边都就绪时**内层赢**（先轮询内层）。

**`timeout` 只写一份**（[`TrTime`] 的**默认方法**，靠 `Self::sleep` + `poll_fn` 组合）
——不让三个后端各写一遍，也就少三处漂移。它是**运行时类型的关联函数**
（`D::timeout(d, f)`），与 `Runtime::block_on(..)` / `Runtime::delay(..)` /
`scope.spawn_local(..)` 同形；后端**不应覆盖**这个默认实现。第 4 条（落后行为）在
实现上各后端略有差异（见 §4），因此**契约测试不做落后态判定**，只做结构性判定。

## 4. 三个后端的实现要点

| 后端 | `sleep` | 周期源 | 备注 |
| --- | --- | --- | --- |
| tokio | `tokio::time::sleep` | 包 `tokio::time::Interval` | 显式取 `MissedTickBehavior::Skip`，向 compio 的「跳过」对齐 |
| compio | `compio::runtime::time::sleep` | 包 compio 的 `Interval` | compio 的语义就是契约原型，**只做包裹** |
| smol | `smol::Timer::after` | **自建** | 见下 |

smol 侧两处必须自己处理：

1. **首次 tick**：`async_io::Timer::interval(p)` 的首次响应落在「一个周期之后」，
   与契约第 2 条不符。自建实现把第一次 `tick` 直接放行，其后交给
   `smol::Timer::interval(p)`——它在**构造时**就把时刻锚定为 `now + period`，此后每响
   一次 `+ period`（见 `async_io` 的 `Stream for Timer`），因此天然满足第 3 条。
   `Timer` 同时实现 `Future<Output = Instant>`，借 `&mut` await 即可（它 `Unpin`）。
2. **零周期**：`async_io::Timer::interval(0)` **不 panic**，而是退化成「每个时刻都
   立即到点」的忙循环。因此本后端**自己断言**（契约第 5 条）。tokio 与 compio 自身
   就会 panic，无需额外处理。

三个后端都必须**包一层本地类型**才能实现 `TrInterval`：trait 来自 `abs_art`、周期源
类型来自外部 crate，孤儿规则不允许直接为外部类型实现外部 trait。

## 5. 为什么额外给 `LocalScope` 也实现一格

业务库手上只有**作用域值**（`S: TrLocalScope`），而 `TrTime` 的能力挂在
`Runtime<CAPS>` 这个**另一个类型**上（`TrDelay` 也是）。补上 `impl TrTime for
LocalScope` 之后，业务库写 `S: TrLocalScope + TrTime` 就够了，**不必再引入第二个
类型参数**——这正是本轮之前识别出来的那个痛点。

只用「类型」不用「值」：计时源来自运行时的线程本地上下文，与作用域值的内容无关。

## 6. 与既有 `TrDelay` 的关系

- **不新增 feature**：新实现挂在既有的 `delay` feature 下。`delay` 与
  `interval`/`timeout` 在三个后端都来自**同一个**运行时能力（tokio 的 `time`、
  compio 的 `time`、async-io 的反应器），拆成两个 feature 只会增加 feature 组合噪音。
- **复用 `DELAY` 能力位**：能力位是「声明」而非实现粒度。若将来确有「要 delay 但
  不要 interval」的场景，再拆位不迟（现在没有）。
- **`TrDelay` 原样保留**，不动它：它已被保活依赖，且是最小原语。

## 7. 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 把 `smux_v1` 的**轮盘**（`Rc<RefCell<BTreeMap>>`）搬进 `abs_art` | `abs_art` 是零依赖、无 `alloc` 的纯抽象 crate；轮盘是数据结构 + 实现，且会把 `embedded-timers` 变成它的公开依赖 |
| 抽象层自带 `TrClock`/`TrInstant` | 在 `abs_art` 里再养一套时间抽象，与 `embedded-timers` 之类重复；且把「绝对时刻」这一消费方关切塞进运行时抽象层 |
| 绝对形式（`sleep_until` / `interval_at` / `timeout_at`）也进 trait | 同上（需要 `Instant` 类型）；而它们对持有自己时钟的消费方**可推导** |
| 让三个后端各自实现 `timeout` | 三处实现 = 三处漂移；`TrTime` 的默认方法一份即可（§3） |
| 把 `timeout` 做成**自由函数**（`timeout::<D, _>(d, f)`） | 运行时类型会退化成一个 turbofish 参数，与家族「能力挂在运行时类型上」的形状不符；改成默认方法后是 `D::timeout(d, f)` |
| 周期源暴露 `tick() -> Instant`（compio 原样） | 需要暴露 `Instant`；消费方若要时刻，读自己的时钟即可 |

## 8. 本次未做 / 遗留

1. **`TrInterval` 是 RPITIT 返回的不透明类型**：消费方能 `let mut iv = T::interval(p);`
   与传参（`impl TrInterval`），但**不能**给那个具体类型起名；`TrTime` / `TrInterval`
   因此**不可 `dyn`**（与 `TrDelay` 现状一致）。
2. **落后行为不统一**（tokio/compio 跳过、smol 补齐）：已按「后端可自行选择」记录，
   消费方不得依赖。若将来要求统一，需要给 smol 自建实现补上「用 `Timer` 交回的
   `Instant` 判断落后」的逻辑。
3. **`abs_art-bridge` / `abs_art-demo` 未跟进**：bridge 的 `delay` feature 已转发，
   因此新 API 自动可用；demo 里暂无计时示例（可后补一组 `cap_time` 示例）。
4. **`elapsed` 文案是中文**（「期限已到」）：与 `smux_v1` 既有文案一致；若家族希望
   错误文案统一成英文，需要一次全局决定。

## 9. `smux_v1` 侧怎么用（下一步）

`smux_v1` 的接法是**减法**：删掉 `src/time` 里的轮盘（`Timer` /
`TimerWheel_` / `TimerKey_` / `Sleep_`），把等待换成 `D: TrTime`，只保留

- **算术与判定层**留在本地（注入式 `Clock`：epoch、空闲毫秒、宽限期判定，
  用假时钟做确定性验收）；
- **等待层**交给后端：`D::delay(..)`、`D::interval(p)`、`D::timeout(d, f)`。

`smux_v1` 需要多一个类型参数 `D: TrTime`（或把 `TrTime` 也加到作用域值的约束上，
见 §5），具体形状在那边落地时决定。

## 10. 未决：RPITIT → 关联类型/GAT（**被 compio 的公开面卡住**）

**为什么想换**：RPITIT 返回不透明类型，签名里**无法**写出 `Send` / `Unpin` 等自动
trait，于是「这个睡眠 future 能不能跨线程投递」在调用方**无法编译期判定**。换成关联
类型（含 GAT）就能把每个后端的具体类型写出来，自动 trait 自然可见。

**查证结果**（tokio 1.53.2 / compio-runtime 0.12.6 / async-io 2.6.0）：

| 成员 | tokio | compio | smol |
| --- | --- | --- | --- |
| 一次性睡眠的 future | `tokio::time::Sleep` ✓ 可命名、`Unpin`（tokio 自己的 `Interval::poll_tick` 里就在 `Pin::new(&mut self.delay)`）、`Send` | **不可命名** ✗：`TimerFuture` 是 `pub(crate)`（`compio-runtime/src/time/future.rs:15`），`sleep`/`sleep_until` 都是 `pub async fn` | `smol::Timer` ✓（字段平实 ⇒ `Unpin`） |
| 周期源**类型** | `tokio::time::Interval` ✓ | `compio::runtime::time::Interval` ✓ | 自建 `Interval_` ✓ |
| `tick` 的 future | **不可命名** ✗（`pub async fn tick`）；但 tokio 另有 `pub fn poll_tick(&mut self, cx)` ⇒ 把 trait 改成**轮询式**即可 | **不可命名** ✗（`pub async fn tick`），且无 poll 版 | 自建，可命名 |
| 超时的 future | `tokio::time::Timeout<F>` ✓ | **不可命名** ✗（`pub async fn timeout`） | 无现成，自建 |

**结论**：`TrDelay::Delay` 与 `TrTime::timeout` 的 future 在 compio 上**没有**可命名
的类型——compio 对外只给不透明 future。因此「全部改成关联类型/GAT」在 compio 上必须
三选一：

- **(A) 上游补口（最优）**：请 compio 公开 `TimerFuture`（或加一个 `Sleep` 类型），并给
  `Interval` 加 `poll_tick`。之后三后端都能给可命名类型、零额外分配、零 `unsafe`。
  **代价：要等上游。**
- **(B) 本地装箱**：compio 侧 `type Delay = Pin<Box<dyn Future<Output = ()>>>`、
  `type Tick<'a> = Pin<Box<dyn Future<Output = ()> + 'a>>`——每次 `delay`/`tick` 一次
  **堆分配**（compio 自己的 `sleep` 因 `TimerRuntime` 的 `BTreeMap` 插入本就分配，
  故这是量上的差别）；`abs_art-compio` 需加 `extern crate alloc`（与 `abs_art-smol`
  同形，仍 `no_std`）。**马上能做。**
- **(C) 折中**：能命名的地方（tokio/smol 的 `Delay`、三者的周期源**类型**）改关联类型，
  `tick` 与 `timeout` 的 future 仍留 RPITIT。收益只有一半。

另有一处与后端无关的取舍：`timeout` 若用**具体结构体** `Timeout<D, F>`（一份实现、
零分配、可命名、Send 由结构决定），内部需要对 `F` 做**结构性 pin 投影** ⇒ 一处
`unsafe` + `PhantomPinned`（`futures::future::Select` 同款）；若改成 GAT
`type Timeout<F>` 由各后端给出，则零 `unsafe`，但变成三份实现，且 smol/compio 仍需装箱。

## 11. 补记（同日）：**用 ITIT 绕过去——不必装箱、不必 unsafe**

上面的 (B)/(C) 建立在一个隐含前提上：「关联类型必须是**具体**类型」。其实不必：
`#![feature(impl_trait_in_assoc_type)]`（ITIT，`smux_v1` 本来就开着这个 feature）
允许在 **impl** 里直接写 `impl Future`：

```rust
impl TrDelay for Runtime<CAPS> {
    type Delay = impl Future<Output = ()>;   // 直接命名 compio 那个 opaque 的 sleep future
    fn delay(d: Duration) -> Self::Delay {
        compio::runtime::time::sleep(d)
    }
}
```

用一个独立探针（已删除）实测了四点，**全部成立**：

1. **自动 trait 会泄漏**——这正是本次改造的动机。调用方
   `assert_send(LocalBackend::delay(..))` 报
   `` `Rc<()>` cannot be sent between threads safely ``；把隐藏类型换成 Send 则通过。
   （对照实验还纠正了一个易错点：**没有 `.await` 点的 async 块，捕获物不跨挂起点，
   反而是 `Send`**——要构造 !Send 必须让捕获物跨越 await。）
2. **关联类型是**可投影**的名字**：
   `struct Holder<D: TrDelay> { inner: Option<D::Delay> }` 能编译 ⇒ 可存进结构体、
   可写 `where D::Delay: Send`。
3. **GAT 与泛型参数都支持**：`type Tick<'a> = impl Future<Output = ()> + 'a;`、
   `type Timeout<F: Future> = impl Future<...>;` 均可用。
4. **「一份实现」与「可命名」可兼得**：把共享逻辑写成 `abs_art` 里的 inherent
   `async fn`（**stable**、自动 trait 照常泄漏），各后端用 ITIT 把它的 opaque 类型
   命名出来：

   ```rust
   type Timeout<F: Future> = impl Future<Output = Result<F::Output, Elapsed>>;
   fn timeout<F: Future>(d: Duration, f: F) -> Self::Timeout<F> {
       timeout_impl::<Self, F>(d, f)
   }
   ```

   探针打印出的类型正是 `timeout_impl::<Backend, F>::{{closure}}` ⇒ **零装箱、零分配、
   零 `unsafe`**，也不必让 `timeout` 变成三份实现。

**因此 §10 的结论改为：采用 ITIT，放弃 (B) 装箱与 (C) 折中。** 代价与范围：

- ITIT 是 unstable feature ⇒ **用它的 crate 变成 nightly-only**。范围可以最小化到
  **只有 `abs_art-compio`**（它的 `Delay`/`Tick`/`Timeout` 三者只能这样命名）**与
  `abs_art-smol`**（`Timeout` 无现成类型；`Delay` 用 `smol::Timer`、`Tick` 用自建包装，
  两者本来就能具体命名）；**tokio 三样都不需要**（`Sleep`、`Timeout<F>` 现成，
  `Tick` 用一个基于 `poll_tick` 的本地包装）。
- **`abs_art` 本身只声明关联类型，可保持 stable**（共享的 `timeout_impl` 是稳定的
  inherent `async fn`）。
- 遗留风险：ITIT 仍在演进（语义/诊断可能变），把后端 crate 钉在 nightly 上意味着
  将来要跟随其变化；若希望家族整体留在 stable，则退回到 §10 的 (A)「请 compio 上游
  公开 `TimerFuture` / 给 `Interval` 加 `poll_tick`」。



## 12. 落地（同日）：关联类型 + **只有 compio 走 nightly**

已按 §11 实施（分支 `feat/time`）。

`abs_art` 侧（**保持 stable、零依赖**）：

| 项 | 形状 |
| --- | --- |
| `TrDelay` | `type Delay: Future<Output = ()>` + `fn delay(..) -> Self::Delay` |
| `TrInterval` | 真正的 GAT：`type Tick<'a>: Future<Output = ()> where Self: 'a` + `fn tick(&mut self) -> Self::Tick<'_>` |
| `TrTime` | `type Interval: TrInterval` + `fn interval(..) -> Self::Interval`；`timeout` 仍是**默认方法**（一份实现），返回本 crate 的**具体结构体** `Timeout<Self, F>` |
| `Timeout<D, F>` | 可命名、零装箱、零分配；内部一处**结构性 pin 投影**（`unsafe` + `PhantomPinned`，SAFETY 注释随码）——本 crate 唯一一处 `unsafe` |
| `UnitFuture<F>` | 把 `Future<Output = T>` 抹成 `Output = ()` 的**安全**适配器（仅在 `F: Unpin` 时实现），供 smol 接 `Timer` |

各后端给出的具体类型：

| 后端 | `TrDelay::Delay` | `TrTime::Interval` | `TrInterval::Tick<'a>` | nightly |
| --- | --- | --- | --- | --- |
| tokio | `tokio::time::Sleep` | `Interval`（包 `tokio::time::Interval`） | `Tick<'a>`（转发 `poll_tick`，**安全**） | 否 |
| smol | `UnitFuture<smol::Timer>` | `Interval`（自建：首次立即 + 锚定） | `Tick<'a>`（轮询 `Timer`，**安全**） | 否 |
| compio | `impl Future`（ITIT） | `Interval`（包 compio 的） | `impl Future + 'a`（ITIT） | **是**（`#![feature(impl_trait_in_assoc_type)]`，家族里唯一） |

验证：

- `cargo test --workspace` **20 个测试目标全绿**（含 **18 格**跨后端契约矩阵——本轮
  又补了一条「`delay(0)` 立即就绪」，它是「等到一个已过去的时刻」这个惯用法成立的
  前提，三个真实后端全部通过）；
- `cargo clippy --workspace --all-targets` 对工作区无新增警告；
- 另加两条**编译期正向断言** `delay_future_is_send`（tokio / smol）：
  `<Runtime<{FULL}> as TrDelay>::Delay: Send` 能通过——这正是本次改造要买的东西
  （自动 trait 不再被不透明类型挡住）。compio 的睡眠 future 是 `!Send`（它的
  `TimerFuture` 内含 `Rc<RefCell<…>>`），因此**不**加这条断言，且在文档里写明。
