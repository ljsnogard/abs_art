# spawn_local 在 tokio / compio / smol 上的行为一致性调研

日期：2026-10-02 12:47
状态：**调研完成；方案已裁决并落地**——人类采纳了下文「路线 1」，
实施记录与验收结果见 [`local_scope-20261002-1307.md`](local_scope-20261002-1307.md)。
本文保留为**证据链**：它记录了「为什么必须值化」的推导过程与实测数据。

---

## 1. 起因

需求来自 `smux_v1`。它的目标是让公开类型上不出现运行时参数 `Rt`
（`MuxConnection<C>` / `MuxCore<C>`），但 `Rt` 目前**必须**留着，因为
`abs_art` 的三个后端对 `spawn_local` 的支持方式差异很大，而 `smux_v1` 的
读 / 写循环正是「`spawn_local` 投递后**立即 `detach()`**、靠消息与取消令牌
自行退出」这一模式。相关背景见
`smux_v1/dev-notes/connection-20261002-0548.md` §17.9（该节把「跨后端
`spawn_local` + `detach` 存活实验」列为最高优先级的实证项）。

本轮的任务是**先做前置冒烟测试**：把 `smux_v1` 真正依赖的契约固化成一条可执行
的测试，再用它去量三个后端的实际行为。**在此之前不改任何 `spawn_local` 实现**
——先有证据，再谈实现。

## 2. 结论速览

### 2.1 实测矩阵（同一份测试体，三个真实运行时）

| 用例 | tokio | compio | smol |
| --- | --- | --- | --- |
| **A** 句柄驱动：spawn 后立即 await `JoinHandle` | ✅ | ✅ | ✅ |
| **B** 运行时驱动：宿主**不 poll 句柄**，等循环自己回报 | ✅ | ✅ | ❌ 宿主永久阻塞 |
| **C** `detach()` 后循环继续被调度 | ✅ | ✅ | ❌ 任务当场被取消 |

复现：`just smoke`（等价于 `cargo test -p abs_art-smoke`）。预期结果就是
**7 过 2 红**——smol 的 B、C 两格是刻意的、已知的缺口。

### 2.2 三条结论

1. **弱形式的用例测不出问题。** 只写「`spawn_local` → 死循环收消息 →
   经 `JoinHandle` 取结果」的话，三个后端**全绿**（用例 A）——因为
   `abs_art-smol` 目前在 `JoinHandle` 被 poll 时会顺带 tick 它自己新建的本地
   执行器，恰好把结果送回来了。**差异只在「宿主不 poll 句柄」时才暴露**
   （用例 B、C）。这一点直接决定了冒烟测试必须写成严格形式，否则它是一张
   假绿条。
2. **问题不是「三个运行时不一样」，而是「本地队列的归属与驱动方式不一样」。**
   compio 根本没有问题（运行时自己持有并驱动线程本地队列）；tokio 的问题是
   **环境前提表达不出来**（纯类型参数说不出「你必须处于 `LocalSet` 内」）；
   smol 的问题是 **`abs_art` 自己造成的**——smol 2.x 不提供 `spawn_local`，
   `abs_art-smol` 只能凭空造一个执行器，并把它绑在句柄上。
3. **让三者一致的改造重点因此是两处**：重写 `abs_art-smol` 的本地队列归属，
   给 tokio 补一个「能携带 `LocalSet` 并驱动它」的值入口。compio 侧基本不动。

## 3. 实测证据

### 3.1 冒烟测试的形状

新增 workspace 成员 `abs_art-smoke`（`publish = false`）：

```text
abs_art-smoke/
├── src/probe.rs     ← 测试体，泛型于 Rt: TrSpawnLocal，一份代码
├── src/harness.rs   ← 独立线程 + 5s 超时的用例骨架
└── tests/spawn_local_contract.rs
                     ← 三个后端的「创建运行时 + 驱动」代码，用同一个宏展开
                       逐字相同的断言逻辑（3 后端 × 3 用例 = 9 条测试）
```

测试体不经过 `abs_art-bridge`：bridge 的 `backend-*` feature 互斥，一次构建
只能启用一个，装不下「三个后端同时横向对比」这个需求；测试体只依赖
`abs_art` 的 trait 与三个后端 crate 的 `Runtime` 标记类型。

**为什么必须给每个用例加独立线程 + 超时**：上述缺口的表现形式是**宿主被永久
阻塞**，而不是返回错误。不加超时，失败会表现为整个测试进程挂死，拿不到任何
可读结论。

### 3.2 失败形态原文

```text
smol_probe_b_runtime_driven ... FAILED
  smol｜B 运行时驱动：5s 内未完成——宿主被永久阻塞，说明任务没有被运行时驱动（本地队列没人推）

smol_probe_c_detach_survives ... FAILED
  smol｜C detach 后存活：投递消息失败：循环的接收端已被丢弃——说明 detach 把任务一起取消了
```

C 的失败形态值得注意：`detach()` 丢弃 `JoinHandle` 时连带丢弃了它持有的
`LocalExecutor`，**任务在 `detach()` 返回之前就已经被析构**，因此连第一条消息
都投不进去。

## 4. 三个运行时的原始能力（源码级事实）

版本：tokio 1.53.1、compio 0.19.2（`compio-runtime` 0.12.6 /
`compio-executor` 0.1.4）、smol 2.0.2（`async-executor` 1.14.0）。

| | tokio | compio | smol 2.x |
| --- | --- | --- | --- |
| 内建 `spawn_local` | 有（自由函数 + `LocalSet` 方法） | 有（= `spawn`） | **无** |
| 对 future 的约束 | `F: Future + 'static`，无 `Send` | `F: Future + 'static`，无 `Send` | 需自行基于 `LocalExecutor` 实现 |
| 本地队列的持有者 | 调用方的 `LocalSet` | 运行时自身 | 无人（要自己造） |
| 谁驱动本地队列 | `LocalSet::block_on` / `run_until` | 运行时的 `block_on` / `wait` | 无人，必须显式 `tick` / `run` |
| 无上下文时 | 自由函数 `spawn_local` **panic** | `with_current` panic | 不适用 |
| `drop(JoinHandle)` | = detach，任务继续 | = **cancel**，任务被取消 | `Task` drop 会 `set_canceled` |
| 原生 `detach` | 无（靠 drop 语义） | 有（`JoinHandle::detach`） | `Task::detach`（只对全局执行器有意义） |

关键 API 事实（决定了候选方案的可行性）：

- **tokio 有非 panic 的值语义入口**：`LocalSet::spawn_local(&self, future)`
  （tokio 1.53.1 `src/task/local.rs:585`）。它的文档明确写着「与自由函数不同，
  本方法**可以在 `LocalSet` 未运行时使用**；投递的 future 会在 `LocalSet` 下次
  启动时开始运行，即使你不 await 返回的 `JoinHandle`」。此外
  `LocalSet::enter()`（同文件 `:533`）是公开的，`LocalSet::run_until`
  （`:712`）与 `LocalSet::block_on`（`:673`）是现成的驱动点。
- **compio 的 `spawn` 本来就不要求 `Send`**：
  `Runtime::spawn<F: Future + 'static>(&self, future: F)`
  （`compio-runtime-0.12.6/src/lib.rs:221`）。因为运行时本身是线程本地的
  （`!Send`），`spawn` 与 `spawn_local` 是同一条队列、同一套语义。
- **compio 的 drop 语义有明文警告**：`JoinHandle` 上的
  `#[must_use = "Drop `JoinHandle` will cancel the task. Use `detach` to run it
  in background."]`，`Drop` 实现里是 `task.cancel(true)`
  （`compio-executor-0.1.4/src/join_handle.rs:148`）。
- **smol 侧的驱动与投递都是现成的**：`async_executor::LocalExecutor` 提供
  `spawn<T: 'a>(&self, future: impl Future<Output = T> + 'a)`（无 `Send` 约束，
  `lib.rs:510`）、`try_tick`（`:597`）、`tick`（`:620`）、
  `run<T>(&self, future) -> T`（`:639`，「驱动执行器直到给定 future 完成」）。
  **缺的只是「谁来持有这个执行器」**。

## 5. 差异的根因归纳

把上表压成三条正交差异，后面所有方案都是在这三条上做取舍：

1. **本地队列的归属**：compio 归运行时；tokio 归调用方的 `LocalSet`；
   smol 无人归（`abs_art-smol` 只好每次调用新建一个）。
2. **谁驱动本地队列**：compio 由运行时的 `block_on` 循环驱动；tokio 由
   `LocalSet` 的驱动点驱动；smol 无人驱动，只能靠 `JoinHandle` 被 poll 时
   顺手 tick（这正是 B 会挂死的原因）。
3. **句柄与任务能否解绑**：tokio 靠 drop 即 detach；compio 有原生 `detach`；
   smol 现行实现把执行器绑在句柄上，detach 等于连执行器一起丢掉。

**由此得到的原因归属**：

- compio：无问题；
- tokio：**契约表达力**问题——纯类型参数 `Rt: TrSpawnLocal` 表达不出
  「必须处于 `LocalSet` 上下文内」这个**环境前提**（类型对了、调用点错了，
  运行期直接 panic）；
- smol：**实现**问题——`abs_art` 把一个本该由「作用域」持有的执行器塞进了
  一次性句柄里。

## 6. 候选实现路线

> **裁决结果：采纳路线 1**（2026-10-02，人类明确同意，并同时提供 `run_until`
> 与 `block_on` 两个驱动入口）。落地细节见
> [`local_scope-20261002-1307.md`](local_scope-20261002-1307.md)。
>
> 关于 `SPAWN_LOCAL` 能力位：初版落地时随 `TrSpawnLocal` 一并删除，随后**经人类
> 论证又原样复职**为「声明位」——位与值各管一件事（位管「你声明了没有」，值管
> 「你拿到了没有」）。经过见
> [`local_scope-20261002-1307.md`](local_scope-20261002-1307.md) §7。
>
> 以下三条的取舍记录保留，作为「为什么不是路线 2 / 3」的依据。

### 路线 1（**已采纳**）：值化的「本地作用域」+ 统一驱动入口

把「本地队列」从一个**隐式的环境**变成一个**显式的值**，让三个后端都能如实
表达自己的前提：

```text
值类型（暂名 LocalScope / LocalSpawner）
  spawn_local<F>(&self, f: F) -> JoinHandle<F::Output>   // 从「类型级关联函数」变成「值上的方法」
统一驱动入口
  Runtime::block_on_local(fut)  // 或 scope.run_until(fut)
```

各后端的映射：

| | 值里装什么 | `spawn_local` 映射到 | 驱动入口映射到 |
| --- | --- | --- | --- |
| tokio | `Rc<LocalSet>` | `LocalSet::spawn_local`（**非 panic**） | `LocalSet::block_on` / `run_until` |
| smol | `Rc<LocalExecutor<'static>>`（每线程一个） | `LocalExecutor::spawn` | `smol::block_on(ex.run(fut))` |
| compio | 空（ZST） | `Runtime::with_current(\|rt\| rt.spawn(f))` | `rt.block_on(fut)`（现状） |

- **优点**：三条差异同时被消掉——队列归属明确（值持有）、驱动明确（统一入口）、
  解绑明确（值存活期间任务就活着，句柄怎么处置都不影响）；tokio 的环境前提从
  「文档约定」变成「类型上拿不到值就 spawn 不了」，编译期就能拦住。
- **代价**：`TrSpawnLocal` 的形状要改（v0.3 刚把 `F` 从 trait 移到方法级泛型，
  这次是把 `Self` 从「类型」变成「值」）；调用方多一步「取得作用域」；
  与 `smux_v1` 期望的「`Rt` 从公开类型上消失」正好同向——`Rt` 可以被一个
  构造期注入的值取代。

### 路线 2：thread-local 隐式本地队列

`abs_art` 在每个线程惰性建一个 `LocalSet` / `LocalExecutor` 存进
`thread_local!`，`spawn_local` 保持无 `self` 的关联函数形状，直接取当前线程
那一份。

- **致命处**：**「谁驱动」仍然没有答案。** tokio 的 `enter()` 只是把上下文设好
  （使自由函数不 panic），**它不会驱动队列**；smol 那边同理。因此仍然必须有一
  个显式的驱动入口，并且要求集成方使用它——问题只是从「环境前提」挪到了
  「驱动入口」，并没有消失。
- 附带代价：隐式全局状态带来嵌套 / 多实例 / 跨运行时语义的复杂度（同一线程
  上先后进两个不同运行时怎么办）。
- 结论：**不推荐**，除非只把它当作路线 1 的降级兼容层。

### 路线 3：只修 smol，tokio 维持文档约定

只把 `abs_art-smol` 改成「执行器不随句柄销毁」，tokio 的 `LocalSet` 前提继续
靠文档 + 调用方自觉。

- 代价：**三个后端仍然不一致**——tokio 多了「必须在 `LocalSet` 内」这条别人
  没有的前置条件，正是 `smux_v1` §17.9 记为硬冲突的第二条。等于只解决了
  一半问题。

## 7. 未决问题与下一步

> 第 1、2 条已随路线 1 的采纳而解决（见 §6 的裁决结果）；第 3、4 条仍然有效。

1. ~~**公开 API 形状待裁决**~~ —— **已裁决**：新增 `TrLocalScope` + 各后端
   `LocalScope`，删除 `TrSpawnLocal`；`SPAWN_LOCAL` 位先删后复职（见 §6 的裁决结果
   与 `local_scope-20261002-1307.md` §7）。
2. ~~**`smux_v1` 的路线 A / B 取舍**~~ —— **路线 A 成立**：本轮证据支持
   「继续用 `abs_art` 抽象可行」——因为 tokio 与 smol 的问题都不是「`abs_art`
   做不到」，而是「原来的形状表达不了」。值化之后 `smux_v1` 可让 `Rt` 从公开类型上
   彻底消失（改为在 `new` 里注入作用域值）。
3. **待补实验**（`smux_v1` §17.9 清单里尚未做掉的两项）：
   - tokio 在 `LocalSet` 之外调用自由函数 `spawn_local` 的 panic 形态——**部分失效**：
     新实现走的是方法版 `LocalSet::spawn_local`，不再有这条 panic 陷阱；
     若要保留「自检」价值，应改为验证「忘记驱动作用域时任务不推进」这一形态；
   - `TrDelay` 是否同病（保活依赖它；若定时任务也是「detach 后不推进」，
     必须与循环一并解决）。
4. **`Send` 回退的代价**：若最终只能给 smol 用 `spawn`（要求 `F: Send`），
   需验证 `smux_v1` 的循环 future 在 `!Send` 传输下是否根本无法满足。
   本轮证据表明**不需要**走这条路——路线 1 的 smol 方案不引入 `Send` 约束。

## 8. 顺带修掉的既有问题

本轮实测时发现 `cargo test --workspace` / `just test` **本来就编译不过**
（与 `spawn_local` 无关）：

- **根因**：`cargo test --workspace` 会把同一个 `abs_art-bridge` 的 feature
  **取并集**——一边是它作为 workspace 成员被启用 `default = ["backend-compio"]`，
  一边是 `abs_art-demo` 缺省演示组经 `bridge_tokio` 请求 `backend-tokio`。
  并集里同时出现两个 backend，触发 bridge 自己的
  `compile_error!("backend feature 只能启用一个")`，整个 workspace 测试编译失败。
- **处置**：把 bridge 的缺省后端改为 `backend-tokio`，与 `abs_art-demo` 的缺省
  演示组保持一致；并在 `abs_art-bridge/Cargo.toml` 里写明「改这里的缺省值必须
  同时改 demo 的缺省演示组」。缺省后端属于**公开约定**，此项变更已获人类同意。
- **连带**：`justfile` 的 `test-backend-tokio` / `test-backend-smol` 本来就因为
  漏写 `--no-default-features` 而必然失败（`--features backend-X` 会与缺省后端
  取并集），一并补上。
- **现状**：`cargo test --workspace` 可以编译并运行，全部通过，**只有
  `abs_art-smoke` 的 smol B、C 两格红**——这两格正是本轮要攻掉的目标。
