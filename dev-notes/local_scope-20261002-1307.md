# 路线 1 落地：值化的本地作用域（`TrLocalScope`）

日期：2026-10-02 13:07
状态：**已实施并通过验收**（3 后端 × 4 用例全绿）
上游调研：`spawn_local-20261002-1247.md`
参考项目：<https://github.com/lexoliu/executor-core>（人类提供）

---

## 1. 决策

采纳调研记录的**路线 1**：把「本地队列」从一个**隐式的环境**变成一个**显式的值**，
并给这个值配上统一的驱动入口。人类明确批准了三件事：

1. 命名：trait 叫 `TrLocalScope`，各后端的值类型统一叫 `LocalScope`（由 bridge 重导出
   同一个名字）；
2. 旧 API 处置：**删除** `TrSpawnLocal` / `HasSpawnLocal` / `SPAWN_LOCAL` 能力位；
3. 驱动入口：**同时**提供 `run_until`（异步原语）与 `block_on`（阻塞便捷入口）。

## 2. 参考项目印证了什么

`executor-core` 的核心设计与路线 1 完全同构，且更早给出结论：

```rust
pub trait LocalExecutor {
    type Task<T: 'static>: Task<T>;
    fn spawn_local<Fut>(&self, fut: Fut) -> Self::Task<Fut::Output> where Fut: Future + 'static;
}

// tokio 的 LocalSet 本身就是那个值
let local_set = LocalSet::new();
let task = LocalExecutor::spawn_local(&local_set, async { /* !Send */ });
```

它连「thread-local 兜底 + 自由函数 `spawn_local`」都做了。**这一条我们刻意没抄**：
调研阶段已经论证过，thread-local 方案解决不了「谁驱动本地队列」——`LocalSet::enter()`
只设置上下文、不驱动队列，问题只是从「环境前提」挪到了「驱动入口」，并没有消失。

另一个没抄的点是它的 `Task::detach` 默认实现 `core::mem::forget(self)`。对 async-task
而言 forget 虽然能让任务继续跑，但会把任务状态机泄漏掉；abs_art 三个后端各自有更精确的
detach（tokio 靠 drop、compio 有原生 `detach`、smol 用 `Task::detach`），继续保留。

## 3. 最终 API 形状

### 3.1 基础 crate

```rust
// abs_art::TrLocalScope
pub trait TrLocalScope {
    type Handle<T>: TrJoinHandle<T> where T: 'static;

    fn spawn_local<F>(&self, future: F) -> Self::Handle<F::Output>
    where F: Future + 'static, F::Output: 'static;

    fn run_until<F>(&self, future: F) -> impl Future<Output = F::Output>
    where F: Future;

    fn block_on<F>(&self, future: F) -> F::Output
    where F: Future;
}
```

两个形状细节值得记下来：

- `run_until` 写成 `fn ... -> impl Future`（RPITIT）而不是 `async fn`。原因是
  `async fn in trait` 会触发 `async_fn_in_trait` 警告（trait 作者无法为返回的 future
  声明 auto trait 约束）。用 RPITIT 后，三个后端的实现都能**直接返回原生 future**
  （tokio 的 `LocalSet::run_until`、smol 的 `LocalExecutor::run`、compio 直接返回 `fut`），
  零包装、零分配，且 edition 2024 会自动捕获 `&self` 的生命周期。
- `Handle<T>` 用 GAT 而不是把 `T` 放在 trait 上——与 `TrSpawnSend` 等的既有形状一致。

### 3.2 三个后端的值

| | `LocalScope` 里装什么 | `spawn_local` | `run_until` | `block_on` | 先决条件 |
| --- | --- | --- | --- | --- | --- |
| **tokio** | `Rc<LocalSet>` | `LocalSet::spawn_local`（方法版，**非 panic**） | `LocalSet::run_until` | `block_in_place` + `Handle::block_on(run_until)` | `block_on` 需多线程运行时且在上下文内 |
| **smol** | `Rc<LocalExecutor<'static>>` | `LocalExecutor::spawn` | `LocalExecutor::run` | `smol::block_on(ex.run(fut))` | 无 |
| **compio** | **零大小** | `with_current(\|rt\| rt.spawn(f))` | `fut` 本身 | `with_current(\|rt\| rt.block_on(f))` | 上下文内（同既有 `TrBlockOn`） |

三点设计后果：

1. **tokio 走方法版 `LocalSet::spawn_local`**（tokio 1.53.1 `src/task/local.rs:585`）。
   它的文档明确写着「与自由函数不同，本方法**可以在 `LocalSet` 未运行时使用**」——
   正是「先建作用域、后驱动」这个用法需要的语义，也顺手消掉了「在 `LocalSet` 之外
   调用会 panic」这条环境陷阱。
2. **smol 的改动最小**：`LocalExecutor` 从 `JoinHandle` 搬进作用域，句柄改走
   `From<smol::Task<T>>`（`local_ex: None`）那条**既有**路径；`JoinHandle` 因此变成
   与 tokio / compio 对称的薄包装。
3. **compio 的空类型不是占位符**：它如实表达「调用方不需要提供任何东西」，与另外两个
   后端形成对照——这正是「值化」想要的效果：需要什么装什么，不需要就是空的。

### 3.3 驱动形态统一

业务/集成两侧的写法变成：

```text
OUTER_DRIVER(scope.run_until(user_future))
  ├─ tokio  : rt.block_on(..)      —— LocalSet 由 run_until 驱动
  ├─ compio : rt.block_on(..)      —— run_until 即 future 本身
  └─ smol   : smol::block_on(..)   —— LocalExecutor 由 run_until 驱动
```

三个后端**逐字相同**，只有最外层 `OUTER_DRIVER` 不同——而创建运行时本来就属于集成方，
bridge 从来只抽象能力、不代建运行时代码。

## 4. 破坏性变更清单

| 变更 | 说明 | 现状 |
| --- | --- | --- |
| 删除 `TrSpawnLocal` trait | 本地投递改由 `TrLocalScope` 值承载 | 保留 |
| 删除 `SPAWN_LOCAL` 能力位与 `HasSpawnLocal` 标记 | 曾使 `FULL` 由 `31` 变为 `23` | **已回滚，见 §7** |
| 删除三个后端的 `Runtime::spawn_local` 固有方法 | 调用点改到作用域值上 | 保留 |
| 后端 feature `spawn_local` → `local_scope` | 名字要与它门控的东西一致 | 保留 |
| 三个后端新增 `LocalScope` 类型 + `local_scope` 模块 | bridge 统一重导出 | 保留 |
| `abs_art-tokio` / `abs_art-smol` 新增 `extern crate alloc` | 作用域内部用 `Rc` 共享队列 | 保留 |

当初删位时，位 3 被留作「已退役位」而不复用给新能力（复用它会让其它能力位数值位移）。
位 3 现已在 §7 中**原样复职**为 `SPAWN_LOCAL`，因此 `FULL` 回到 `31`，
`SPAWN_BLOCKING` 等其它位的数值始终未变；`caps.rs` 的
`bit_assignment_is_stable` 单测把整套位号钉住。

## 6. 下一步 / 遗留

1. **`smux_v1` 要跟着改**：它现在用 `Rt: TrSpawnLocal` + `Rt::spawn_local(..).detach()`。
   换成作用域值之后，`MuxConnection` 可以改成 `new(scope: &LocalScope, ..)`——`Rt` 因此
   真的能从公开类型上消失（这是 `smux_v1` §17.9 的目标）。注意它依赖的是**已发布的
   git 分支**，要等本次改动推上去。
2. **`SMUX` 侧是否需要持有作用域的克隆**：`LocalScope` 已实现 `Clone`（tokio/smol 共享
   同一条队列、compio 是 `Copy`）。若 `MuxConnection` 想自己持有队列以保证「连接活着
   队列就活着」，可以直接存一个克隆——公开类型上仍然不出现 `Rt`。
3. **待补实验**（调研笔记 §7 列的另外两项，本轮未做）：
   - `TrDelay` 是否同病（保活依赖它）；
   - `Send` 回退的代价——本轮证据表明**不需要**走这条路。
4. **`Runtime::block_on` 能否也顺带驱动本地队列**：本轮把驱动入口放在作用域上，
   `TrBlockOn` 行为未变。若将来希望「只调 `Runtime::block_on` 也能推进本地任务」，
   那是另一项 API 决策。

## 7. 追加决议：能力位以「声明位」身份回归

日期：2026-10-02 13:22（人类提出并拍板）

### 7.1 人类的反驳

> 「位能力本来就是一种写在代码上的 RBAC 而不是能力剪裁的话，就是最大的存在价值，
> 值得加回来——也即，如果调用者真正想越过这个仪式获取它没有授予的能力，迫使他做
> 这个动作本身就有价值。」

这个论证推翻了本文原先「位在值存在后不再门控任何东西，因此冗余」的判断。原判断
**对了一半**：位确实不再门控**调用点**（那是值的职责，且这点必须保持，否则
「类型对了、调用点错了就 panic」的坑会回来）。但位还有另一半职责没被看到——

### 7.2 位与值各管一件事

| | 回答的问题 | 载体 |
| --- | --- | --- |
| 能力位 `SPAWN_LOCAL` | 你**声明**了没有？ | `Runtime<CAPS>` 的类型级标记 |
| 作用域值 `LocalScope` | 你**拿到**了没有？ | 实现 `TrLocalScope` 的具体值 |

位是**声明**：它拦不住真想用的人（把位写上就够了），但强制他先把这件事写下来，
于是「某库开始使用本地投递」必然出现在类型别名、diff 与 code review 里，也能被
`grep` 出来。最贴切的类比不是权限系统，而是 **`unsafe`**：任何人都能写，但必须写。

**为什么这个类比是对的、而「RBAC」这个类比要打折扣**：授予者与被授予者是同一个人
（库作者），没有第二方同意，所以它不是授权机制。它约束的是**意外**，不是**恶意**。
但这个价值是真实的——review 时的可见性、CI 上的 `grep`、以及「一个声称与运行时
无关的库悄悄依赖了本地投递」这类漂移，都靠它拦住。

### 7.3 落地的形状

位**不**重新门控 `Runtime::spawn_local`（那个方法不复存在，见 §4），而是门控
**作用域的声明式构造入口**：

```rust
impl<const CAPS: usize> Runtime<CAPS>
where
    [(); CAPS]: HasSpawnLocal,
{
    pub fn local_scope() -> LocalScope { LocalScope::new() }
}
```

- `SPAWN_LOCAL` 原样复职位 3（`1 << 3`），`FULL` 回到 `31`，其它位数值未变；
- 三个后端各自提供该关联函数；bridge 重导出 `SPAWN_LOCAL`；
- **已知且刻意保留的漏洞**：`LocalScope::new()` 仍是公开入口，因此绕过声明可行。
  人类此次只批准「把位加回来」，未批准收窄 `new()` 的可见性。若要让它有 `unsafe`
  那样的约束力，需要把 `new()` 退到 `pub(crate)`、只留声明路径——那是**另一项**
  公开 API 变更，尚未讨论。

### 7.4 新增的验收点

| 用例 | 位置 | 判定 |
| --- | --- | --- |
| `declared_cap_gives_usable_scope` | 三个后端各一份 | `Runtime::<{SPAWN_LOCAL}>::local_scope()` 取得的作用域可用 |
| `bit_assignment_is_stable` | `abs_art` | 位号未位移：`SPAWN_LOCAL == 8`、`FULL == 31` |
| `local_scope_requires_declaration` | `abs_art-demo`（`compile_fail`） | `Runtime::<{BLOCK_ON}>::local_scope()` 编译不过 |
| `no_spawn_local_on_runtime_type` | `abs_art-demo`（`compile_fail`） | 即便 `FULL`，`Runtime` 上也没有 `spawn_local` |

正反两侧都有，因此 `compile_fail` 不会因为「方法根本不存在」而假通过。

### 7.5 未采纳的相关提议

人类明确指示：**本次不做 `abs_art-bridge` 的 feature 能力定制**（即通过 bridge 层
feature 选择「后端支持哪些能力」）。实测确认这条通路目前确实不存在：bridge 对
`abs_art-*` 的依赖没有 `default-features = false`，`backend-*` 一开就把五个能力全拉
进来。将来若需要「运行时支持但不提供给业务代码」这种**由集成方控制**的边界，那才是
正确的机制（位是业务库自己写的，给不了这个边界）。
