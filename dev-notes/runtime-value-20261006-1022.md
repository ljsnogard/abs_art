# v0.4 运行时「值化」：把能力从关联函数改成 `&self` 方法

日期：2026-10-06 10:22
分支：`feat/abs_art-runtime`（回退点：`feat/time` @ `dca6e20`）
性质：**设计决策 + 实施记录**（本轮改动生产代码）
前置阅读：`runtime-tag-scope-clock-20261006-0923.md`（第一轮实测：tag 形态不可行、
`abs_art` 给不出默认 B、thread-local 队列的代价、`TrClock` 的约束边界）。

---

## 0. 一句话

把运行时从「类型标签」变成「**值**」：所有能力 trait 的方法收 `&self`，本地队列、
计时器、时刻源都由**同一个运行时值**提供。于是「哪条本地队列」「哪个时钟」不再可能
被指向别处——v0.3 的两处「串」（独立作用域值与独立时钟配置）从结构上消失。

## 1. 为什么必须动（因果链）

第一轮讨论留下的三件事，指向同一个根因：**能力与环境分离**。

| 症状 | v0.3 的形状 | 后果 |
| --- | --- | --- |
| 本地投递要「位 + 值」两件套 | 位在 `Runtime<CAPS>` 类型上，值是一个**独立的作用域对象** `LocalScope` | 「用哪个运行时」与「驱动哪条队列」是两件事；值可以脱离类型单独传递 |
| 时钟与计时器可能不同源 | `TrDelay::delay` 挂在运行时类型上，时刻由消费方配置（`TrConnCfg::Clock`） | tokio `start_paused` 下「睡在虚拟时钟、读在墙上时钟」，空闲超时永不触发（已实测） |
| 库侧被迫穿类型参数 | 能力全是**无 `self`** 的关联函数，调用点必须命名运行时类型 | 业务库写 `Rt: TrSpawnSend` + `S: TrLocalScope`，两个参数都只为「指向那份环境」 |

第一条的修法有三个候选（第一轮实测）：
把 `Runtime` 定义进 `abs_art`（薄形态 `E0117` 不可行；厚形态需一族 `Backend*` trait，
代价大），或者**让运行时本身成为值**——后者不动 `abs_art` 的抽象层结构，只是把
「能力怎么被调用」改掉，改动面反而最小、语义收益最大。

关键判断：**「哪个运行时」本来就是一个运行期事实**。把它编码成类型标签（ZST）只能
让类型正确、调用点错误——第一轮 §2.2 的「跨线程静默新建队列」「忘写 `run_until` 就
静默挂死」都是这条的实例。值化之后，同一件事由「你手里那个值」回答。

## 2. 抽象层改了什么（`abs_art`）

### 2.1 trait 形状对照

| trait | v0.3 | v0.4 |
| --- | --- | --- |
| `TrAsyncRuntime` | `fn about() -> RuntimeTag` | `fn about(&self) -> RuntimeTag` |
| `TrSpawnSend` | `fn spawn<F>(future: F) -> Self::JoinHandle<..>` | `fn spawn<F>(&self, future: F) -> Self::JoinHandle<..>` |
| `TrSpawnBlocking` | `fn spawn_blocking<F,T>(f: F) -> ..` | `fn spawn_blocking<F,T>(&self, f: F) -> ..` |
| `TrBlockOn` | `fn block_on<F>(f: F)` | `fn block_on<F>(&self, f: F)` |
| `TrDelay` | `fn delay(d) -> Self::Delay` | `fn delay(&self, d) -> Self::Delay` |
| `TrTime` | `fn interval(p) -> Self::Interval`；`TrTime: TrDelay` | `fn interval(&self, p)`；`TrTime: TrDelay + TrClock` |
| `TrLocalScope` | `spawn_local(&self, ..)` / `run_until(&self, ..)` / **`block_on(&self, ..)`** | 保留前两个；**删掉 `block_on`** |
| `TrClock` | 无 | 新增：`type Instant; fn now(&self) -> Self::Instant` |

### 2.2 `TrLocalScope::block_on` 为什么删掉

值化之后 `TrLocalScope::block_on(&self, f)` 与 `TrBlockOn::block_on(&self, f)` 签名
完全相同；同一个运行时值同时实现两者时，`rt.block_on(f)` 会成为歧义调用。而它们的
语义本来就该合一：**这次阻塞等待要驱动的东西，就是这个值拥有的东西**（本地队列、
计时器）。删掉本地那份，保留 `TrBlockOn` 作为唯一的阻塞驱动入口。

### 2.3 `TrClock`：同源成为类型约束，但**不新开能力位**

- `TrClock` 的 `Instant` 用**结构约束**表达（`Copy + Ord + Add<Duration, Output=Self>
  + Sub<Self, Output=Duration> + 'static`），不引入外部时钟抽象 crate；第一轮已实测
  `std::time::Instant` / `tokio::time::Instant` / `embedded-timers` 的 `Instant64` 与
  `TimespecInstant` 全部满足，且约束非空（`f32` 反例 `E0271`）。
- `TrTime: TrDelay + TrClock`：**拥有周期能力 ⇒ 必须能报时刻，且报的是它自己的时刻**。
  这直接堵死「真计时器 + 外来时钟」的错配；要注入假时钟，就构造一个假的运行时**值**
  （实现 `TrDelay + TrClock`，二者必然一致）。
- 残留洞（诚实记录）：类型相同 ≠ 时间基准相同。`type Instant = tokio::time::Instant`
  却用 `Instant::from_std(std::time::Instant::now())` 取时刻仍然合法。类型系统只能钉
  名字，钉不住基准；**默认路径的同源由后端实现保证**，不是类型系统保证。
- **没有新增 `CLOCK = 1<<5` 能力位**：`TrTime` 已经是 `TrClock` 的超 trait，若再让
  `TrClock` 单独受一位门控，就会出现「有 `TrTime` 却没有 `CLOCK` 位」的非法组合，
  或迫使 `impl_has!` 表从 80 个数字扩到 192 个（第一轮已实测可行，但那是**独立**决定）。
  因此本轮 `TrClock` 与 `TrDelay` 共用 `DELAY` 位；「时钟该不该有自己的声明位」留作
  待裁决项（见 §6）。

### 2.4 能力位模型不变

`Runtime<CAPS>` 的 `CAPS` 仍然只是**这个值类型的形状参数**：掩码决定该类型实现了哪些
能力 trait，从而决定哪些方法可调。「想用就得写下来」这条设计意图一字未改——而且
**现在真的门控调用点了**：`SPAWN_LOCAL` 没写时 `rt.spawn_local(..)` 直接编译失败
（v0.3 里 `local_scope` 位只门控「取作用域的入口」，`LocalScope::new()` 仍可绕过）。

## 3. 后端改了什么（以 tokio 为样板）

`Runtime<const CAPS: usize = FULL>` 从 ZST 变成值：

```rust
pub struct Runtime<const CAPS: usize = FULL> {
    handle_: tokio::runtime::Handle,                 // spawn / spawn_blocking / block_on 打在它上面
    #[cfg(feature = "local_scope")]
    local_: Rc<tokio::task::LocalSet>,               // 本地队列归这个值所有
}
```

- 构造：`Runtime::current()`（要求运行时上下文）、`Runtime::with_handle(handle)`
  （上下文之外构造）、`retag::<{..}>()`（换 CAPS 标签）；crate 级自由函数
  `current() -> Runtime<FULL>` 解决「表达式位置不带 turbofish 会 `E0284`」的推断问题。
- `Clone` = 共享同一个句柄与**同一条**本地队列。
- 删除了独立的 `LocalScope` 类型；`impl TrLocalScope for Runtime<CAPS>`。
- 代价：持有 `Rc<LocalSet>` 时值是 `!Send`。这是诚实的——本地队列本来就绑定线程；
  需要跨线程用全局能力时，在目标线程各构造一个值（`with_handle` 支持这么做）。
- 需要 `with_handle` 而不是只留 `current()` 的原因：值的构造不再是无条件的，而集成方
  常常需要在「还没有进入运行时」的位置先把值准备好。

## 4. bridge 改了什么

- `LocalScope` 重导出删除；`Runtime` 现在是**值类型**，裸名按 cfg 解析，另给具名别名
  `TokioRuntime` / `CompioRuntime` / `SmolRuntime`（多后端同存时用）。
- 新增 `current()` 重导出（默认后端的构造入口）。
- **新增「多后端必须显式声明默认」守卫**（`default-backend-*` feature）。依据是第一轮
  P5 探针的实测：
  > `cargo build --workspace` 会把各成员的 feature 取并集。应用只要 smol，但并集里
  > 还有 tokio 时，裸名按优先级选中 tokio，二进制走 tokio 路径却没人建 tokio 上下文
  > → 运行期 panic：`there is no reactor running ...`。而 `cargo run -p app_smol` 正常。
  > **「确定性优先级」只保证给定 feature 集合时选谁确定，不保证集合是对的。**
  守卫规则：启用 ≥2 个 backend 且**没有**声明 `default-backend-*` → `compile_error!`；
  声明了 ≥2 个 → `compile_error!`；只启用 1 个时它就是默认，不必声明。

## 4.1 后端侧的实测结论（子任务汇总）

- **compio 能真正钉住运行时**：`compio::runtime::Runtime` 是可 `Clone` 的 `Rc` 句柄簇，
  有 `current()`，`spawn` / `spawn_blocking` / `block_on` 全收 `&self`。所以它不是
  「环境式 ZST」，值抓住的就是那份运行时（构造函数命名 `with_runtime`、escape hatch `runtime()`）。
- **smol 有一个固有限制**：`smol::spawn` 用进程级 `static GLOBAL: OnceCell<Executor>`
  且常驻后台线程驱动——**任何值都钉不住它**；能钉住的只有本地队列
  （`Rc<LocalExecutor>`）。这一点已如实写进 `spawn_send.rs` 文档，并用两个测试
  （「值 drop 后任务照跑」「两个值共享同一条全局队列」）把它变成可执行判定，而不是
  伪造「每值一份全局执行器」的假象。smol 的 `spawn_blocking`（`smol::unblock`）同理。
- **compio / smol 的 `TrClock::Instant` 用 `std::time::Instant`**，且是唯一「与计时器
  同源」的选择：compio 根本没导出自己的时刻类型，async-io 的计时器内部就是
  `std::time::Instant`。代价是这两个 crate 的 `#![no_std]` 要显式 `extern crate std;`
  ——它们本来就无条件依赖 std，不新增任何依赖。
- **tokio 的 `block_on` 有前提（多线程运行时），smol/compio 没有**；compio 的值甚至可以在
  上下文之外 `block_on`（内部自己 `enter`）。这些差异都写进了各自的模块文档。

## 5. 代价与未决

1. **运行时值必须被构造**：v0.3 的 ZST 随处可写，现在要有句柄/上下文。`delay`-only
   的用法也被要求处于 tokio 上下文（`Runtime::current()` 需要 `Handle::current()`）。
2. **`!Send`**：tokio/smol 的值持有 `Rc`。需要一个只含全局能力的 `Send` 把手
   （`RuntimeHandle`）吗？未做，留作待裁决。
3. **`CAPS` 在值类型上**：两个不同 CAPS 的值是不同类型，需要 `retag` 转换；这是
   「能力位是类型级声明」与「运行时是值」两件事叠加的必然结果。
4. **`TrClock` 没有独立能力位**（§2.3），若将来要求「只读时刻、不要等待」，需要新位 +
   扩表。
5. **自由函数面的声明纪律**：如果将来在 bridge 上加 `delay()`/`spawn()` 之类自由函数
   （第一轮 §6 的提案），它们会以 `Runtime<FULL>` 实例化，调用点无法表达「我只要
   `BLOCK_ON`」——v0.3 精心设计的声明纪律会在最方便的路径上失效。真要做，需要给自由
   函数加 `const CAPS` 参数或按能力分组。
6. **`#[inline]` 是零成本的必要条件**：P5 的 LLVM IR 对照显示，bridge 的转发自由函数
   不加 `#[inline]` 时下游 IR 残留 7 个转发调用点，加上后为 0。任何「零成本转发」面
   都要显式加 `#[inline]`（或要求下游开 LTO）。

## 6. 待裁决

1. 是否补一个 `Send` 的 `RuntimeHandle`（只暴露全局能力）？
2. `TrClock` 是否要独立能力位（`CLOCK = 1<<5`，表扩到 0..=63）？
3. 是否在 bridge 上加「默认 runtime 的自由函数面」（第一轮 §6 的提案）？若加，能力位
   声明纪律怎么保（§5.5）。
4. 三个后端的语义差异要不要统一（smol 的全局执行器无法被值钉住；compio 的运行时本身
   是线程本地的）——本轮按「能做到多少写多少 + 文档写清」处理。

### 7.2 三个后端的形状差异（都是「如实表达」，不是巧合）

| | tokio | compio | smol |
| --- | --- | --- | --- |
| 值里装什么 | `Handle` + `Rc<LocalSet>` | `compio::runtime::Runtime`（`Clone` 的 `Rc` 句柄簇） | `Rc<LocalExecutor>`（+ 全局执行器无法被值钉住） |
| 构造函数 | `current()` / `with_handle()` | `current()` / `with_runtime()` | `current()` / `with_executor()` |
| `spawn_local` | 投到值持有的 `LocalSet` | 与 `spawn` 同一入口（队列归运行时） | 投到值持有的 `LocalExecutor` |
| `run_until` | 驱动值持有的 `LocalSet` | **≡ 直接 await**（运行时自己驱动） | 驱动值持有的 `LocalExecutor` |
| `block_on` 前提 | 需多线程运行时上下文（`block_in_place`） | 值可自行 `enter`，**上下文外也可用** | 无先决条件 |
| `TrClock::Instant` | `tokio::time::Instant`（虚拟时间可暂停） | `std::time::Instant`（compio 未导出自己的时刻类型） | `std::time::Instant` |
| 值是否 `!Send` | 仅在开 `local_scope` 时 | 恒为 `!Send`（运行时本身线程本地） | 恒为 `!Send` |

smol 的固有限制：`smol::spawn` 是**进程级**全局执行器，值钉不住它；值能钉住的只有本地队列。
compio 的 `TrSpawnSend` 在语义上退化为线程本地队列（运行时 `!Send`），已在模块文档写明。

### 7.3 值化之后 `compile_fail` 用例的写法陷阱（对全家都有用）

能力方法改收 `&self` 之后，`<Type as Trait>::method(args)` 这种**静态调用形式**在被调用
方法**存在但约束不满足**时，报的是 `E0061`（少一个 receiver 参数）而不是
`E0277`（trait bound 不满足）。于是旧的 `compile_fail` 用例会「以错误的理由失败」——
测试仍然是绿的，但它证明的东西变了。

修法：负向用例一律写成**值上方法调用**（`let rt = ...::current(); rt.spawn(..)`），
与真实调用点一致；并尽量在 `compile_fail` 上绑定期望错误码（`compile_fail,E0599` /
`compile_fail,E0373`），把它变成「失败原因也正确」的机器证明。

另外两条旧的负向用例在 v0.4 下**不再成立**，已删除并记录原因：
`no_spawn_local_on_runtime_type`（`Runtime` 上现在真的有 `spawn_local`）与
`tag_is_full_only`（`tag()` 现在是对所有 `CAPS` 的固有方法）。

### 7.4 值化带来的一个真实摩擦（值得记下来）

`abs_art-smoke` 的契约测试原本把探针抽成「收一个闭包」的公共入口
（`fn case<F>(f: F) where F: FnOnce(&Rt) -> Fut`）。值化之后探针要收 `&R` 并返回
**借用该值**的 future，而 `FnOnce(&R) -> F` 这种约束**表达不了「返回值与入参借用同期」**
（闭包不产生 higher-ranked 的返回类型），于是出现一批
`lifetime may not live long enough`。

修法有两条，各有代价：

1. **内联骨架**（探针实现采用）：每个用例自己写「造值 → 探针 → 驱动」三行，
   不在用例之间抽公共入口。代价是重复三行骨架，好处是「值在哪个上下文里造出来」
   一眼可见。
2. **装箱**（未采用）：`for<'a> FnOnce(&'a R) -> Pin<Box<dyn Future<Output = T> + 'a>>`。
   能抽公共入口，但每个用例多一次堆分配，且把「零成本」的测试体变成装箱体。

这条与 API 设计相关：**运行时值以 `&R` 进入异步函数时，返回的 future 天然借用它**
——这正是值语义的应有之义（future 运行期间必须保证那个运行时还在）。消费者写
`async fn foo<R: TrTime>(rt: &R) -> ... { rt.delay(d).await }` 是自然的；但把它当作
「可自由传递的回调」传进高阶函数时需要显式处理生命周期。
